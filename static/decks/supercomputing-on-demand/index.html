60 seconds of contextLustre looks nothing like NFS

Sixty seconds of context for the storage people — bear with me, because the shape of this filesystem is exactly why the driver is interesting. Lustre splits metadata from data: an MDT holds the namespace, and OSTs hold the data, with every file striped across targets. Clients don't go through a single server like NFS — they talk to every OST directly over LNet, which is a network of NIDs, not IPs-with-users. Crucially for us: Lustre was built for one trusted organization with thousands of nodes, not mutually-distrusting tenants. Multi-tenancy arrived late — nodemaps for client identity, project quotas for accounting — and it shows. That's the puzzle: mapping a cloud multi-tenancy model onto primitives that were never designed for it.

"Your filesystem, behind the API your researchers already have."

And sixty seconds for the OpenStack side, because half of you came here from SC. Manila is the shared filesystem service — think "Cinder for files." A share is a first-class cloud resource: size, protocol, access rules, lifecycle — and crucially, self-service with quotas and revocation, which is what ticket queues do badly. It already speaks NFS, CephFS, GPFS, a dozen vendor arrays. What it didn't speak — until this month — was the filesystem that runs most of the TOP500. That's the gap.

the designManila's abstractions → Lustre's primitives

Manila conceptLustre primitivethe hard part
sharesubdirectory of a mounted clientone filesystem, many tenants — no per-share servers (DHSS=False)
size / extend / shrinkproject quota (lfs setquota -p)quota is the capacity — the guest's df shows it as the volume size
access rule (ip)nodemap + NID rangeidentity is a network address on the fabric — deny-by-default, per-share maps
manage / unmanageadopt an existing directorybrownfield: read the size back from the project quota

Designed in the open with the Lustre Collective — layered for what's coming: ID ranges (2.17) → key-based identity & LQA (2.18+)

So how do you fit a parallel filesystem into Manila's model? A share is a subdirectory on a filesystem the operator already provisioned — no share servers, because nobody wants a VM between them and their OSTs. The elegant trick is capacity: Manila's share size IS a Lustre project quota — the guest mounts and literally sees the quota as the volume size in df. Extend and shrink are quota changes, live, no remount. Access control maps an IP rule to a nodemap NID range — deny-by-default comes free. And manage-existing adopts a brownfield directory: set a project quota, call the API, your twenty-year-old genomics store is now a Manila share. Every one of these choices went through public review with the Lustre Collective — and the design is deliberately layered so that as Lustre grows real multi-tenancy — per-nodemap ID ranges, key-based client identity, LQA — the driver grows with it. what you just sawThree hard problems, solved with filesystem primitives

📦Provisioning
mkdir + project id + quota — atomic enough to be an API, boring enough to be reliable. A dedicated provider network is the storage fabric, just like Sanger did by hand.
⚖️Quota enforcement
not a polite number in a database — the filesystem returned EDQUOT. Self-service extend is a quota change, visible live in the guest.
🔐Access control
no rule → no mount, enforced by the MGS. Revoke closes the door to new mounts. RO rules map to read-only nodemaps.
Quick recap of what just happened, because the elegance is in what the enforcement points are. Provisioning: a directory, a project id, and a quota — primitives so boring they're reliable. Quotas: enforced by the filesystem itself — that EDQUOT came from Lustre, not from Manila pretending. And the self-service extend — that's the ticket-eliminator: the researcher hit a wall and fixed it themselves in ten seconds. Access control: deny-by-default at the MGS, grants are nodemap ranges, revocation closes new mounts. This is what "designed for multi-tenancy from the filesystem up" looks like when the filesystem wasn't — you use the primitives it does have, honestly.

honesty slideWhat it doesn't do yet

  • Snapshots & revert — not wired to Lustre snapshots yet
  • Connected clients survive revocation — nodemaps gate new mounts; eviction of live connections is roadmap
  • Ephemeral NIDs are the tax — IP-based rules mean the driver tracks fabric addresses; key-based client identity in Lustre 2.18 fixes this properly
  • root inside the guest bypasses project quotas on kernels without root_prj_enable — harden your guests
  • Nodemap inheritance is sharp — new nodemaps inherit deny_mount from the default map (found building this very demo; fix pending review)
  • Shrink, replication, QoS — on the roadmap, in the open
Every talk should have one of these slides. No snapshots yet. Revocation gates new mounts but doesn't evict clients that are already connected. The real tax is that access rules are IP-based — because that's what nodemaps know today — which means tracking ephemeral fabric addresses; Lustre 2.18's key-based client identity is the real fix and the driver is designed to adopt it. Root inside a guest can bypass project quotas on older kernels. And my favorite: while building this very demo I found that new nodemaps inherit deny-mount from the default nodemap — meaning a hardened default silently breaks Manila's grants. Found it live, filed it, fix is in review. That's what designing in the open gets you — and it's exactly the kind of sharp edge this talk exists to sand down.

The driver was designed to grow with Lustre — each primitive the filesystem adds becomes a Manila feature.

One more slide on where this goes, because the design is deliberately layered onto Lustre's own roadmap. Today — shipped in Hibiscus — we use nodemaps and project quotas: subdirectory shares, quota-as-capacity, IP access rules. As Lustre 2.17's per-nodemap ID ranges and root quotas land, we get uid mapping per tenant and a defense against guest root. The big one is 2.18's key-based client identity — real credentials instead of tracking ephemeral network addresses, and the driver's access layer was built to swap that in. Snapshots are next up, then eviction-on-revoke, shrink, replication. The principle: every primitive Lustre grows becomes a Manila feature — the driver tracks the filesystem, not the other way around.
