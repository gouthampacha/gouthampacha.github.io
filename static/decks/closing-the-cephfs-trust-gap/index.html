30-second primerManila

  • OpenStack Shared File Systems service
  • Self-service RWX, POSIX shares at scale
  • Abstracts dozens of backends behind one API
  • It's the control plane — not in the data path
  • First of the major IaaS platforms — designed 2013, shipped 2015 (before AWS EFS was announced; years before GCP Filestore)
For the newer folks — thirty seconds on the blue zorilla. Manila is OpenStack's shared filesystem service: tenants ask for POSIX, read-write-many shares, and get them, self-service. It abstracts dozens of wildly different backends behind one API — and it's the control plane only, never in the data path, which is going to matter a lot in about four slides. And a little pride, because we earned it: we weren't following the hyperscalers here — we were ahead of them. Manila shipped in 2015, before AWS EFS was even announced, four years before GCP Filestore existed. I won't claim they copied us — but when every major cloud added managed file storage, they hit the same wall we'd been dismantling in public: multi-tenant isolation, one API over wildly different backends, self-service lifecycle. We have the scars and the API to show for it. [advance]

what multi-tenant shares must enforceTwo guarantees

Data isolation
strict namespaces; no root escape into another tenant's tree
✓ solved everywhere
Network path isolation
tenant data traffic secured from other tenants
△ hard & nuanced — where native CephFS falls down
A shared filesystem has to pass two tests before it's safe for multi-tenancy. Test one: data isolation — your namespace is yours, and no credential lets you wander into someone else's tree. Every backend passes that one — it's table stakes. Test two: network path isolation — the traffic between a client and its storage has to be protected from other tenants. [tap the cracked shield] This is the one that's hard, nuanced… and exactly where native CephFS falls down. Which is our next slide, and it's a little painful.

why native CephFS falls short“CephFS is for trusted users” — the Ceph community

  • CephFS is great: POSIX, performant, HA, scalable —
  • ① Cooperative quotas — the client is trusted to stop writing. A compromised client won't.
  • ② Clients sit on the Ceph public network — every tenant VM can reach & probe your storage daemons
Let me be fair to CephFS first: it's genuinely excellent — POSIX, fast, horizontally scalable, survives hardware failures with a shrug. But the Ceph community has said, in writing, for years: 'CephFS is for trusted users.' Two reasons. One: quotas are cooperative — the MDS asks the client to stop at the limit, and a compromised client's answer is… no. Two, and this is the one that should make you squirm: to mount native CephFS, the client must sit on the Ceph public network. Same network as your MONs, MDSes, OSDs. [point at the VM inside the red box] Look where the tenant VM is. It's not near your storage cluster — it's a PEER of your storage cluster. It can probe your daemons, and depending on your msgr2 configuration it can potentially watch cross-tenant traffic go by. People build heroic structures to contain this — per-tenant Ceph filesystems, special provider networks — and even then, trusted tenants aren't protected from each other. [beat] There has to be a better answer.

the established answerNFS-Ganesha: better, but not enough

  • ✔ Familiar NFS security; only the gateway touches the Ceph network
  • ✘ HA is hard — active/active, no auto-rebalance
  • ✘ Placement, cache-coherency, an extra service to run
  • ✘ Performance: network hop + userspace overhead
The established answer: put a gateway in front of it. NFS-Ganesha — and credit where due, Manila pioneered supporting this. It genuinely works: familiar NFS access control, and only the gateway touches the Ceph network. Tenants stay outside. But look at the price tag. High availability is genuinely hard — active/active Ganesha doesn't auto-rebalance clients when a node dies. There's placement and cache-coherency to babysit. It's another service on your pager. And performance: a network hop plus userspace overhead — published throughput tests put Ganesha around half of native, and it varies a lot by workload. [shrug] Better security. Real costs. It's the security tax, paid in bandwidth and on-call pages.

enter virtiofsWhat if attaching a share were as easy as attaching a volume?

$ openstack server add volume …
=
$ openstack server add share …

No gateways · No expensive isolated networks · Security by construction

The design goal was almost cheeky: make attaching a shared filesystem feel exactly like attaching a block volume. One API call. No gateway to run, no bespoke per-tenant network architecture. You say 'server add share' the same way you say 'server add volume' — and the share just… appears in the VM. Security and simplicity, by construction. That's it. That's the feature. The rest of the talk is why it's safe and what it unlocks.

what virtiofs actually isBuilt for hypervisor–guest locality

  • Purpose-built for hypervisor–guest locality — not a network FS bolted onto VMs
  • Guest ⇄ host over virtqueues (VIRTIO); FUSE server-side; hiprio queue
  • Created at Red Hat — now a community effort across Kernel, QEMU, FUSE, Kata, OpenStack
virtiofs is not a network filesystem that got bolted onto VMs — it was purpose-built for the one place where a network is silly: when the guest and the host are literally on the same machine. A daemon called virtiofsd runs on the host. The guest talks to it over virtqueues — shared-memory rings — virtiofsd answers as a FUSE server, done. On Linux the guest needs zero new packages; the driver's been in the kernel for years. It started at Red Hat and it's now a genuine community effort across the kernel, QEMU, FUSE, Kata, and OpenStack. [point at the cyan line] And notice the line in the middle: the guest's entire filesystem universe is one daemon. Hold that thought — it's the whole talk.

the thesisThe trust boundary moves

From “tenants respect the rules” → to “the hypervisor enforces the rules”

[slow down. This is the slide.] Native CephFS: security depends on tenants respecting the rules — the VM sits inside the red zone. Ganesha: better — the tenant's at the edge, but you pay the gateway tax. virtiofs: [trace the arrow with your hand] the guest talks to ONE thing, virtiofsd. The cephx credentials live on the hypervisor — the layer you control — and never, ever inside the guest. The trust boundary moves from 'tenants respect the rules' to 'the hypervisor enforces the rules.' [beat] Say it with me internally one more time: the boundary moves to the hypervisor. That's where it belongs. Everything else tonight is just evidence.

the attack surface shrinksBlast radius

Today: network to the whole cluster + a cephx keyring
With virtiofs: blast radius = one directory

Bonus: the trusted host is now the Ceph client — cooperative quotas are enforced against the guest

Let's talk blast radius, because this is what your security team actually asks. Compromised guest today: network reachability to your ENTIRE Ceph cluster, plus a cephx keyring as a souvenir. Same guest with virtiofs: virtqueues to one daemon — seccomp-filtered, no network namespace, pivot-rooted into a single directory. If virtiofsd itself falls, it has no network and can see exactly one folder. And a bonus people always miss: quotas. CephFS quotas are cooperative — they hold because the client agrees to stop. With virtiofs, the client is the trusted host, not the guest. Cooperative quotas become ENFORCED quotas. The attack surface collapses and the quota story gets fixed in the same move. Two gaps, one boundary.

bonusWindows guests finally get RWX

Windows has no clean native NFSv4.1 client — virtiofs doesn't care what backs the share.
(honesty: needs the virtio-fs driver + WinFsp in the guest — maturing, not magic)

A bonus that surprises everyone: Windows. Windows has no clean native NFS 4.1 client — which has made NFS shares a non-starter for whole categories of Windows workloads. virtiofs doesn't care what's behind the share — the guest sees a virtiofs device either way. Honesty footnote, because I promised you the engineer's version: the guest needs the virtio-fs driver plus WinFsp. It's maturing fast, but it's a driver install, not magic. Still — read-write-many shared storage for Windows VMs, from the same one-liner. That alone unlocks render farms, CAD, and every legacy app that expects a mapped drive.

demoServing an open LLM (Llama-3-70B) at scale

Enough slides. Let me show you, with a story everyone in this room has lived: you're serving an open LLM — say Llama-3-70B — and the weights are a hundred and forty gigabytes. Question one: how do you run ten replicas without copying 140 gigs into every single VM? Question two — the one that matters tonight — do you really want all of those VMs on your Ceph storage network? [beat] Watch. Six beats: secure attach, where the weights actually live, instant scale-out, protecting the registry, live-migrating a serving replica — and a finale where a jailbroken agent VM tries to escape and fails. Everything you'll see is a real command with real output.

demoServing an open LLM at scale — 6 acts · every line is a real command with real output

▶ auto-plays · space pause/resume · ← → seek · 0–9 jump · narrated live with the act-by-act script (press S)

Act 1 (secure attach): inference-01 is serving the model. There are the actual weight files — safetensors shards, config, tokenizer — right there in the VM. Now watch these three lines like a hawk: no ceph client, no keyring, NO route to a storage network. [point at the caption] This VM is serving a CephFS-backed model and has no idea Ceph exists. The weights arrive over virtiofs.

Act 2 (where the weights live): So where are the 140 gigs? Here — mounted once, on the hypervisor. One copy on the host. virtiofsd re-exports that single directory into the VM — sandboxed — and the cephx identity it uses is scoped to exactly this model's path and namespace. The operator owns the key. The tenant never sees it. Least privilege as a lifestyle.

Act 3 (scale out): Traffic spikes. inference-02 joins the fleet and mounts the SAME registry — no 140-gig download, no second copy, and the weights verify bit-for-bit. And RWX isn't just for reading: ops publishes a LoRA adapter once — [if anyone asks: 'LOR-ah', low-rank adaptation, a megabyte-scale fine-tuning patch swapped in at serving time] — and every replica sees it. No redeploy. And notice: each replica got its own cephx identity. Revoke one, the others don't blink.

Act 4 (protect the registry): Now the fun part — I try to delete the model out from under my own live replicas. [point] Blocked — 403, resource lock. Because the hypervisor is HARD-mounting this share, letting a user yank it mid-flight could hang the whole compute node — every VM on it, not just theirs. And that access list, viewed as the tenant? The keys are masked. Primitives we built in Manila for exactly this.

Act 5 (live migration): The headline. inference-01 is answering requests right now — one log line per request. I live-migrate it to another host. [let it play, don't talk over the landing] …It lands on compute-02 in about fifteen seconds. The model stayed mounted the entire time. The request log: zero dropped. The number-one blocker for production adoption — falling, in real time.

Act 6 (the finale): And the same boundary that protects the model protects you FROM the workload. Let's role-play: this VM is a jailbroken, prompt-injected agent, and it's looking for a way out. [mime looking over its shoulder] No keyring. No ceph.conf. Nothing in the environment. The storage subnet isn't even in its routing table. Untrusted code goes in — nothing sensitive comes out. Its entire world is one directory. And that's the same 'server add share' from Act 1.

guardrails we had to inventNew safety rails in Manila

  • Resource Locks — block delete / abandon while in use (atomic, stackable)
  • Visibility Locks — hide cephx identity & key from the tenant: Access Key: ******
  • Useful beyond virtiofs
A confession: we broke things in interesting ways while building this. Because the host does the mounting, a user deleting a share mid-mount could hang the compute node — every VM on it, not just theirs. One tenant's cleanup should not become everyone's outage. So we taught Manila new reflexes: resource locks — atomic, stackable — that block deletion while a share is in use. And visibility locks, which hide the cephx identity and key from the tenant's own access list — infrastructure metadata they should never see. You watched both fire in Act 4. And here's the thing — these are useful even if you never touch virtiofs. That's the best kind of side effect.

the headlineLive migration: the #1 production blocker — falling

  • Upstream pieces landed: QEMU 9+ · libvirt 10+ · virtiofsd 1.11+
  • VM moved hosts in seconds, share mounted throughout, no gaps in the request log
  • Nova mirrors block-volume live migration semantics
I want to dwell here, because this is the slide your operations team cares about. Without live migration you can't do host maintenance without application downtime — which means no kernel updates, no evacuation, no sleep. The upstream pieces only recently lined up — QEMU 9, libvirt 10, virtiofsd 1.11 — and on Nova's side it mirrors how block volumes migrate. What you just watched: a VM with its CephFS share live-migrated in about fifteen seconds, mounted the whole way, no gaps in the request log. [honesty beat] Light load — the claim is the mount, not throughput. But the blocker? It's falling. And it's the community's number-one priority, because it's the gateway to evacuation and the full HA story.

the bigger ideaBlock is for one writer. Files are for everyone.

Today's easy path — RWO block volume
cripple to one replica (no HA, no rolling updates) — or become your own storage operator with a SPOF
RWX POSIX as a first-class primitive
many readers & writers on one POSIX tree — HA, rolling updates, shared state

Pitch: RWX by default. Reach for block only for true single-writer raw devices.

Now zoom out, because this is bigger than Ceph. Almost every stateful application ever written — web roots, caches, datasets, checkpoints, model weights — assumes a shared POSIX filesystem. But what's the easy path on every cloud? A block volume. Read-write-ONCE. One writer. So teams 'share' by either crippling their app to a single replica — say goodbye to HA and rolling updates — or by standing up their own NFS server on top of a block volume. Congratulations: your tenant is now a storage operator, with a single point of failure and a pager. [beat] That's backwards. Files are for everyone; block is for the rare true single-writer. My pitch, and I mean it literally: RWX by default.

the AI angleOne copy, many consumers

  • LLM serving's real storage pain = model weights (70B ≈ 140 GB)
  • RWX: mount weights once, every replica reads them → fast autoscale, no per-replica download
  • One host mount → N VMs on that host share one page-cache copy of the weights — works today
  • DAX (roadmap — needs libvirt support): guests map that cache directly — zero per-VM copies
  • The AI headline isn't MB/s — it's one copy, many consumers
Let me make the AI case concrete, because it's the most fun. The real storage pain in LLM serving isn't throughput — it's the weights. 70 billion parameters, roughly 140 gigabytes. You want many inference replicas sharing ONE copy, not each one pulling 140 gigs from object storage on every cold start while your autoscaler drums its fingers. RWX is the exact fit: mount once, every replica reads. And here's today's sleeper: every replica on a host reads through the same single host mount — so the host kernel keeps ONE page-cache copy of the weights feeding all of them. A per-VM network mount physically cannot do that. DAX — roadmap, it needs libvirt support and lands after memfd — upgrades this to zero-copy, guests mapping that cache directly. But 'one copy, many consumers' isn't the roadmap. It's how it works today. The AI headline isn't megabytes per second — it's ONE copy.

beyond inference — the 2026 problemThe killer sandbox: untrusted agent code

  • Real POSIX workspace, no storage client · no key · no storage network — a jailbroken agent has nothing to steal, nowhere to pivot
  • Fleet of ephemeral sandboxes share one read-only repo + toolchain (one host copy; one RAM copy w/ DAX)
  • Per-sandbox cephx identity — scope data in, revoke at task end; results write to a shared dir, no egress path
  • Lineage: Kata Containers already runs virtiofsd for exactly this · (QEMU/Cloud-Hypervisor path; not Firecracker, not confidential VMs yet)
If you remember one 'beyond inference' idea, make it this one — and it's not a stretch, it's where the pattern was BORN. Kata Containers — whose entire product is 'run untrusted code in an isolated VM' — chose virtiofsd as THE mechanism for handing the sandbox its filesystem. Now hold that up against the 2026 problem: you're running untrusted, model-GENERATED code, and a container with a service-account token mounted in it is… not the boundary you want. [beat] Put the agent in a VM. It gets a real POSIX workspace — repo, tools, package cache — shared read-only off ONE host mount, instant startup. And when — not if — the agent gets prompt-injected, it has nothing to steal and nowhere to pivot: no storage client, no key, no route. Blast radius: one directory. Then the hygiene: per-agent scoped data, revoked the moment the task ends — a clean-room per agent — and results written to a shared dir your orchestrator reads. No egress path needed. Caveats, because engineer's version: this is the QEMU/Cloud-Hypervisor/Kata lineage — Firecracker deliberately said no to virtiofs, different road — and confidential VMs still collide with the shared-memory parts. But for mainstream 'isolate untrusted agent execution'? Same primitive you just watched serve a model.

Everyone jumps to AI, but the interesting part is WHY this is more than another shared filesystem. Three levers nobody else has. One: nothing in the guest — no client, no key, no route. Two: the guest is decoupled from the backend — it only ever sees a tag; the operator owns what's behind it. Three: one host mount fans out to many guests through a shared page cache. And from those levers: Windows finally gets RWX. Fleet content fan-out — publish once, thousands of VMs read one host copy; think CDN origin living on your hypervisor. Compliance — 'zero tenant-held storage secrets' is a sentence auditors frame and hang on walls; government, finance, healthcare, sovereign clouds. And more: storage refresh as vMotion-for-files, immutable OS fleets, air-gapped enclaves, multiattach that's actually safe. [beat, then the pre-emption] One honest caveat before someone else says it: confidential VMs — SEV-SNP, TDX — are the one place this doesn't fit yet. Encrypted guest memory collides with shared-memory filesystems. Frontier, not feature.

not an OpenStack-only ideaThe industry is converging

And this isn't an OpenStack-only idea — the whole industry is converging on it. Kata did it first, for sandbox isolation. Nova does it now, for VMs — that's tonight. KubeVirt does it in virt-launcher, for VMs on Kubernetes. One clarification worth making crisply, because it's a lovely subtlety: CSI and virtiofs never actually meet. Manila CSI's job ends when the share is mounted on a node — if the consumer is a pod, that mount IS the delivery, and it works today. If the consumer is a VM, virtiofsd picks up from there. Same shares, same trick, different mediator — and the guest can't tell which one delivered its filesystem. That's decoupling all the way up the stack. Three ecosystems, one pattern. We're not early — we're right on time.

where we areRoadmap — closing the remaining gaps

Where we actually are — the engineer's version, no rose tinting. The base feature shipped in Epoxy. Cold migration and resize shipped in Hibiscus — that's real, it's out. In flight: hot attach, so you don't stop the VM; live migration — which you watched working on a dev branch; memfd, which deletes the memory-backing gymnastics and is the item operators will love; and after memfd, the DAX window for zero-copy guests. And one more class I won't hide: lifecycle parity, per operation. Rebuild, evacuate, shelve/unshelve, cross-cell — every op that moves or recreates an instance must re-establish the mount, and each lands on its own. Same machinery, op by op — it's the honest tail of the roadmap. [beat] Live migration is priority one. Come help. Testers and reviewers are the actual bottleneck.
