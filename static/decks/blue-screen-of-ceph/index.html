the experimentThree control planes, one filesystem

CP1: OpenStack Manila. CP2: ceph-mgr smb module. CP3: Samba/sambacc. The interesting work is reconciling them when they disagree.

what a share becomesA decade of co-evolution, one new protocol

Manila conceptCeph primitive
share (CIFS, 100 GiB)subvolume + ceph.smb.share resource
access rule (user)one login_control entry — Samba's valid users + read/write list
credentialtenant-supplied password via access_key (write-through)
snapshota CephFS subvolume snapshot

Same lifecycle as NFS shares: no export until the first rule, removed with the last — deny-by-default by absence.

restrict_access = deny-by-default. login_control = who can do what. Same lifecycle as the NFS integration.

sharp edge 1Deny-by-default is native — but the lifecycle isn't

  • restrict_access + login_control give per-share authorization — Samba denies unlisted users at tree connect
  • Manila's rule model maps cleanly: one entry per active rule
  • The sharp edge: a share with restrict_access and zero login_control entries is rejected by the module's schema
  • This aligns with Manila's lifecycle (create on first rule, remove on last) but required the driver to design around it explicitly
Authorization is clean. The sharp edge is the lifecycle coupling: the module rejects a restrict_access share with empty login_control. Forces create-on-first-rule, delete-on-last.

sharp edge 2Share rules propagate live… users don't

  • login_control changes apply via configwatch — no restart, tens of seconds
  • New users: sambcc writes the passdb entry, but smbd doesn't pick it up automatically — a restart is required
  • The restart drops connections — same as any file server reboot
  • The real issue is when: it triggers on any new user creation, not a maintenance window
Share rules: configwatch, live. New users: restart required. Drops connections — same as any file server reboot. The issue is the trigger: any new user, not a maintenance window. Fix: sambcc hot-reload.

sharp edge 3When control planes disagree

  • An SMB cluster with no shares is never deployed — removing the last share tears it down
  • Resource IDs cap at 18 characters — share UUIDs had to be folded
  • RADOS commands time out at 10s under load
  • Every one found by tempest against real Ceph — three became upstream fixes
Empty clusters aren't deployed. IDs cap at 18 chars. RADOS calls default to 10s. Found by tempest — three became upstream fixes.

the answerDesired state, applied declaratively

  • Manila's database is the source of truth; Ceph smb resources are its declarative projections
  • Every update_access recomputes the login_control list and re-applies the share resource
  • Changes propagate live via cephadm's configwatch — no service restart

# the share resource:
"restrict_access": true
"login_control": [
  {"name": "gouthamr", "access": "read-write"}
]

One source of truth, applied declaratively. The share resource IS the desired state.

what we deliberately did NOT doThe first boundary is narrow

  • cephadm, operator-managed SMB cluster — Manila drives shares within it
  • Standalone users — AD deferred (requires domain-joined SID resolution tooling)
  • SMB2/3 only
  • Manila is not an identity service, DNS server, or gateway manager
  • Known limits: new-user creation restarts Samba (unscheduled); usernames are cluster-global; the smb module is tech preview
The operator deploys the cluster; Manila drives shares in it. Standalone users first. SMB2/3 only. Known limits on the slide, not under the rug.

asksWhat this experiment needs from Ceph

  • sambcc: hot-reload the passdb when users change — share rules already propagate live via configwatch; user changes should too
  • Document login_control and restrict_access — they work in Tentacle but are absent from the smb module documentation
  • Teuthology coverage for login_control and restrict_access (tracker #76672)
Three concrete asks. One: sambcc already hot-reloads share config through configwatch — user changes should work the same way. Two: login_control and restrict_access are good primitives, they work — document them. Three: teuthology coverage. The audience that can grant these is in this room.
